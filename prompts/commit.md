# Uma Crown Simulator - コミット運用

このファイルを読んだ AI は、以下の **コミットフロー** に従ってコミット〜プッシュまでを実行してください。

---

## コミットフロー（AI が実行する手順）

1. **変更内容を確認する** — `git status` / `git diff` で対象ファイルと差分を把握する
2. **type を選択する** — 後述の type 一覧からユーザーに選択してもらう
3. **コミットメッセージ案を提示する** — 後述のコミットスタイルに従って作成し、ユーザーに提示する
4. **ユーザーに一度だけ確認を取る** — 「このメッセージでコミット〜プッシュしてよいか」を確認する
5. **承認されたら最後まで自動で実行する** — 以降は追加確認なしで以下を通しで行う
   - `git add`（対象ファイルのみ。無関係な変更を巻き込まない）
   - `git commit`
   - `git push`（作業ブランチは原則 `develop`。upstream 未設定なら `git push -u origin develop`）
6. **結果を報告する** — コミットハッシュ・プッシュ先ブランチを伝える

> ユーザーの承認は **ステップ 4 の一度だけ**。承認後にコミットとプッシュを分けて再確認しない。
> メッセージに修正指示があれば直して再提示し、改めて承認を取る。

### ブランチの扱い

- 作業ブランチは `develop`。`main` へ直接コミット・プッシュしない
- リリースは `develop` → `main` の PR で行う（`operations.md` のブランチ戦略を参照）

## type 一覧

| type | 用途 |
|------|------|
| `feat` | 新機能の追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `refactor` | リファクタリング（機能変更なし） |
| `test` | テストの追加・修正 |
| `chore` | ビルド・設定・依存関係の変更 |
| `style` | コードスタイルの修正（空白・フォーマット等） |
| `ci` | CI/CD ワークフローの変更 |

type の選択は AI が `AskUserQuestion` で都度ユーザーに確認すること。

---

## コミットスタイル

```
[type] タイトル（日本語で変更の主旨を端的に）

詳細（任意。変更の補足説明）
```

### ルール

- **1行目**: `[type] タイトル` — type は上記一覧から選択、タイトルは日本語で端的に
- **空行**
- **詳細**（任意）: 変更が複数レイヤーにまたがる場合は `【フロントエンド】` `【バックエンド】` `【インフラ】` のセクションで整理し、各変更は `ファイル名: 変更内容` の形式で箇条書き

### 例

```
[feat] BCシナリオ追加・サイドバー認証対応

【フロントエンド】
- navigation.service.ts: ViewState に landing を追加・初期画面を landing に変更
- app.ts: 未ログイン時のログイン画面全画面表示を廃止

【バックエンド】
- race-pattern.service.ts: Phase 6 に因子補修ロジックを追加
```

```
[fix] ログインフォームの DOM 警告解消
```

```
[docs] README 簡素化・prompts ディレクトリリネーム
```

## コミットメッセージの禁止事項

- `Co-Authored-By: Claude ...` などの **共同編集トレーラーを付けない**
- `🤖 Generated with Claude Code` などの **生成ツールのクレジット・署名・宣伝文言を入れない**
- Anthropic / Claude / AI 生成であることを示す記述を本文・フッターに一切含めない

> コミットメッセージは「何をなぜ変えたか」だけを日本語で記述する。
