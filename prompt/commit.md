# Uma Crown Simulator - コミット運用

このファイルを読んだ AI は、以下の **コミットフロー** に従ってコミット〜プッシュまでを実行してください。

---

## コミットフロー（AI が実行する手順）

1. **変更内容を確認する** — `git status` / `git diff` で対象ファイルと差分を把握する
2. **コミットメッセージ案を提示する** — 後述のコミットスタイルに従って作成し、ユーザーに提示する
3. **ユーザーに一度だけ確認を取る** — 「このメッセージでコミット〜プッシュしてよいか」を確認する
4. **承認されたら最後まで自動で実行する** — 以降は追加確認なしで以下を通しで行う
   - `git add`（対象ファイルのみ。無関係な変更を巻き込まない）
   - `git commit`
   - `git push`（作業ブランチは原則 `develop`。upstream 未設定なら `git push -u origin develop`）
5. **結果を報告する** — コミットハッシュ・プッシュ先ブランチを伝える

> ユーザーの承認は **ステップ 3 の一度だけ**。承認後にコミットとプッシュを分けて再確認しない。
> メッセージに修正指示があれば直して再提示し、改めて承認を取る。

### ブランチの扱い

- 作業ブランチは `develop`。`main` へ直接コミット・プッシュしない
- リリースは `develop` → `main` の PR で行う（`operations.md` のブランチ戦略を参照）

---

## コミットメッセージの禁止事項

- `Co-Authored-By: Claude ...` などの **共同編集トレーラーを付けない**
- `🤖 Generated with Claude Code` などの **生成ツールのクレジット・署名・宣伝文言を入れない**
- Anthropic / Claude / AI 生成であることを示す記述を本文・フッターに一切含めない

> コミットメッセージは「何をなぜ変えたか」だけを日本語で記述する。

---

## コミットスタイル

- **1行目**: 日本語で変更の主旨を端的に（例: `BCシナリオ追加・サイドバー認証対応`）
- 空行
- 変更が複数レイヤーにまたがる場合は `【フロントエンド】` `【バックエンド】` `【インフラ】` のセクションで整理
- 各変更は `ファイル名: 変更内容` の形式で箇条書き
- 小さなバグ修正は `バグ修正: 〇〇` の形式
- リファクタリングは `〇〇 リファクタリング・〇〇拡充` の形式
